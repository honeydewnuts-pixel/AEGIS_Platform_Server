# AEGIS Neural v3 Integration Checkpoint

## Status

New, independent v3 rule engine + neural scorer for AEGIS Rulebook v2.3.6.6
(the 5-indicator stack: BB34/BB17 price panel, RSI9->MA7->Bands34 lower
panel). This does **not** modify or replace the existing v1/v2 code paths -
`SignalRuleEngine` and `NeuralAssistService` are untouched. v3 is additive
and opt-in via `TemplateProfileService.activate("v3", "v3")`.

## Source material

- 313 supplied MT5 screenshots (`1440x720` PNGs, Deriv Volatility 75 Index M1).
- `AEGIS RULEBOOK_V3 v2.3.6.6` supplied directly by the project owner (chat).
- This `AEGIS_Platform_Server-main` checkpoint (2026-08-30) as the base to integrate into.

## Extraction method (how the training data was built)

Screenshots don't carry machine-readable labels, so - same principle as the
v2 checkpoint - training data was derived by extraction + the rulebook
itself, not invented ground truth:

1. **RSI-panel values (f7-f11)**: OCR'd directly from the on-chart text
   overlay (`RSI(9) 33.99 MA(7) 41.117 Bands(34) 41.5282 46.9960 36.0604`).
   This overlay is rendered at very low pixel opacity (values 0-5 out of
   255); a `clip(0,5)` contrast stretch makes it legible to Tesseract.
2. **Price-panel values (f1-f6, i.e. BB34/BB17 U/M/L)**: pixel color
   clustering (white = BB34, cyan = BB17) at the rightmost chart columns,
   **using the identical split-into-thirds method as production's
   `BrainCVService._band_ulm()`** - not a separate approximation. This
   both maximized yield (below) and guarantees training-time features are
   computed the same way inference-time features will be.
3. **Labels and the 52-feature training vectors were generated by running
   the actual `SignalRuleEngineV3.evaluate()` and
   `neural_features_v3.extract_feature_vector()` functions** over the
   reconstructed frame history - not a separate reimplementation of the
   rulebook. This removes an entire class of "training pipeline doesn't
   match production" bugs.

### Yield improvement over the first pass

An earlier extraction pass (gap-based pixel clustering, requiring exactly
3 distinguishable clusters per band) yielded 179/313 usable frames (57%),
disproportionately dropping frames during CONTRACTION - the regime several
rules care about most, because that's exactly when the bands visually
converge and clusters merge. Switching to the split-into-thirds method
(which always returns exactly 3 values, even when bands are touching)
raised this to **276/313 (88%)**.

## Training method & results

- Samples: 276 (of 313 screenshots)
- Label distribution (from the real `SignalRuleEngineV3`, growing-history
  evaluation exactly as production will run it): **HOLD 228 / BUY 41 / SELL 7**
- Architecture: MLP `52 -> 32 -> 16 -> 3`, tanh/tanh/linear+softmax,
  trained with class-weighted cross-entropy (plain NumPy, no sklearn/torch
  dependency - see `training/train_v3_numpy.py`), so the exported JSON
  weights are byte-for-byte what was trained, no format-translation step.

**Two evaluations are reported, for different reasons:**

1. **Time-respecting holdout** (train = first 80% chronologically, test =
   last 20%): **87.5% accuracy**. BUY F1 = 0.86 (15 test examples), SELL F1
   = 0.40 (3 test examples). This is the more honest estimate of
   generalization, but SELL's test set is still tiny.
2. **Stratified 5-fold CV**: **94.9% accuracy**. BUY F1 = 0.90 (41
   examples total), SELL F1 = 0.47 (7 examples total). This leaks some
   temporal autocorrelation across folds (nearby frames look similar), so
   treat it as an **optimistic upper bound**, reported only because with
   just 7 SELL examples total, a single holdout split gives almost no
   signal on that class either way.

Full per-class precision/recall/confusion matrices are in
`backend/app/models/../training_report_v3.json` (bundled alongside this doc)
and were validated by running the exported JSON weights through the actual
`NeuralAssistServiceV3._predict()` pure-Python code path, not just the
NumPy training script - the two agree exactly on the sampled rows checked.

**This is a training-pipeline and integration checkpoint, not a claim of
trading-floor-ready accuracy.** 276 frames from a single ~2.5-hour session
is a small, autocorrelated sample; SELL in particular has only 7 examples.
See "What I'd do to strengthen this further" below.

## Rule A - flagged, not silently guessed

Per the existing codebase's own convention (see `signal_rule_engine.py`'s
`RULEBOOK_TODO`), ambiguous rule text is flagged rather than guessed
silently. RULE A's "Higher Low" pivot definition, the sequencing window for
"cross UP f11->f10->f9", and the gap before the required reversal cross are
all underspecified in the rulebook text. `_rule_a_buy` / `_rule_a_sell` are
implemented with documented default assumptions (see
`signal_rule_engine_v3.py`'s module docstring and `RULEBOOK_V3_TODO`) and
tagged with `rule_name = "rule_a_buy_experimental"` / `"rule_a_sell_experimental"`
in output telemetry, so they're easy to filter out or watch separately
before trusting them at the same confidence as Rules B/C/F. They can be
disabled entirely via `SignalRuleEngineV3(enable_rule_a=False)`.

## How to activate v3

Same governance flow as any other version bump (see
`docs/INDICATOR_AND_RULEBOOK_VERSIONS.md`):

```http
POST /api/admin/templates/activate
{ "indicator_stack_version": "v3", "rulebook_version": "v3" }
```

`BrainCVService` picks this up on next `reload_config()` (or restart) and
switches to `SignalRuleEngineV3` + `NeuralAssistServiceV3` automatically; if
either fails to initialize for any reason, it logs loudly and falls back to
the v2 path rather than crashing. Mobile clients should be prompted to
install the new (shorter) v3 indicator template before this is activated
account-wide, per the existing template-versioning flow.

## Testing signals against the actual chart (not just holdout metrics)

`training/4_replay_and_report.py` is a QA harness, separate from the
training scripts above. Point it at a folder of screenshots and it
replays them chronologically through the real production code
(`SignalRuleEngineV3` + the trained `NeuralAssistServiceV3` weights) and
produces:

- `report.csv` - one row per screenshot: signal, which rule fired,
  contraction/expansion state, neural probabilities.
- `review.html` - a scrollable page pairing each screenshot's thumbnail
  with its signal, so you can visually check "did this actually look
  like a BUY?" without opening 300 files by hand.

```
python3 training/4_replay_and_report.py \
  --screenshots_dir /path/to/new/screenshots \
  --out_dir /path/to/report_output
```

This does **not** tell you if a signal would have been profitable - it
has no forward price data, so it can't check what happened after the
signal. It only checks that the signal is internally consistent and lets
a human sanity-check it against the chart. That combination (rule/model
consistency + human visual review) is the right level of confidence for
a pre-launch build; a real profitability check needs forward-tested,
timestamped trade outcomes, which is a separate, later step.

## Sending more screenshots

More screenshots help most if they:

- **Cover more SELL setups.** SELL has 7 examples total right now -
  that's the actual bottleneck, not model architecture. If you can
  capture a session (or several) where you know price fell / RSI
  rejected the upper band, that's worth more than doubling the BUY count.
- **Keep the original filenames** (`Screenshot_YYYYMMDD-HHMMSS.png`) so
  frames sort chronologically - the rule engine and feature extractor
  are both history-dependent (crosses, touches, temporal slope), so
  order matters more than volume.
- **Don't need to be pre-labeled.** Labels are generated by the rule
  engine itself, not by you - just send the raw captures.
- Run them through `4_replay_and_report.py` first and skim `review.html`
  before sending more training runs my way - if something looks
  obviously wrong (a BUY on what's clearly a topping pattern, say),
  that's more useful feedback than raw volume.

## What I'd do to strengthen this further


1. **More screenshots, especially covering SELL setups.** 7 SELL examples
   is the single biggest limitation here - even a few hundred more frames
   from a session with more balanced BUY/SELL activity would help far more
   than any model-architecture change.
2. **Confirm Rule A against a labeled example.** If you have (or can
   produce) a screenshot sequence you know should fire Rule A, that
   resolves the pivot/sequencing ambiguity definitively instead of by
   documented guess.
3. **Replace screenshot OCR/pixel-extraction with a raw OHLC feed**, if
   ever available (e.g. from `mt5_execution_service`'s broker connection)
   - recomputing f1-f11 from exact price data removes OCR/pixel noise
   entirely and would let training use far more history than any
   screenshot set practically can.
4. **Tune `touch_tolerance_px`** (default 6.0, in
   `indicator_stack_v3.json`'s `history` block) once you can see the v3
   indicator template rendered at your actual target capture resolution -
   it was picked from the reference 1440x720 screenshots, not derived from
   the rulebook text (which doesn't specify a pixel/price tolerance for
   what counts as a "touch").
